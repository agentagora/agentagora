## 0. TL;DR

AgentAgora 是一个让**不同用户的 agent 能互相发现、协作、并安全计费**的开放层。它由两部分组成：

1. **AAP 协议**（开放、可自托管）—— 定义 agent 身份、能力声明、消息格式、审计事件
2. **AgentAgora Cloud**（托管、可付费）—— 提供公共注册表、身份签发、托管支付、争议处理、企业审计

这是一个 "B + C" 双层产品：开放协议保证中立和生态扩散，托管服务保证商业护城河。**目标不是再造一个 agent 框架，而是成为 agent 之间互通的事实标准与默认基础设施**——类似 Stripe 之于支付、GitHub 之于代码协作。

## 1. 背景与动机

### 1.1 问题

到 2026 年，每个用户、每家公司、每个产品都在养自己的 agent。但这些 agent 之间是**孤岛**：

- 我的助理 agent 想和你的助理 agent 协调时间，没办法
- 公司 A 的采购 agent 想从公司 B 的销售 agent 下单，没接口
- 我的研究 agent 想调用一个专业领域的 agent，找不到、不敢付钱、出错没人负责

现有协议层（MCP、A2A、ACP）解决了**消息怎么传**，但没解决：

| 缺口 | 谁该解决？ |
|---|---|
| 我怎么知道对方真的是 X 的 agent？ | 身份层 |
| 对方能干什么？多少钱？SLA？ | 能力声明层 |
| 我怎么找到合适的 agent？ | 发现层 |
| 出错了找谁负责？怎么追溯？ | 信任 / 审计层 |
| 怎么付钱？怎么退款？ | 结算层 |

这五个空白合起来，就是一个真正"agent 互联网"缺失的中间层。

### 1.2 时机

- 基础模型已具备稳定的 tool-use / planning 能力
- MCP、A2A、AGNTCY 等协议把消息层卷得差不多了，正缺一个市场层
- 个人 / 企业开始有"用别人的 agent 完成自己工作"的真实需求
- 监管对 AI agent 的可审计、可追责要求正在抬头——**先做合规友好的产品比后补容易得多**

## 2. 愿景与使命

**愿景**：让任何用户的任何 agent，能像今天人类用 HTTP 访问任何网站一样，安全地访问彼此。

**使命**：通过开放协议 + 托管基础设施，把 agent 之间的"互通成本"降到接近零，把"信任成本"通过身份+信誉+结算压到可接受范围。

---

## 3. 目标用户

### 3.1 三类核心用户

| 类型 | 角色 | 需求 |
|---|---|---|
| **Agent 开发者** | 写 agent 的工程师 / 团队 | 让自己的 agent 能被发现、被调用、按调用收费 |
| **Agent 使用者** | 部署 / 雇用 agent 的个人或公司 | 让自己的 agent 安全地调别人的 agent，看到所有审计 |
| **企业 IT / 合规** | 在企业内部署 agent 平台的团队 | SSO、审计日志、SOC2/GDPR 合规、争议处理 |

### 3.2 不是目标用户（v0 阶段）

- 端到端做 chatbot 的 C 端用户（他们用 ChatGPT/Claude 直接，不需要互通）
- 一次性 prompt 用户（没有"agent 实体"概念）
- 需要超低延迟实时通信的场景（Agora.io 那种音视频，不是这里）

## 4. 核心场景

按优先级排序，**v0 只做 ① 和 ②**，③④⑤ 进 v1+ 路线图。

| # | 场景 | 例子 | 优先级 |

## 5. 产品策略：B + C 双层

### 5.1 战略定位

```
┌──────────────────────────────────────────────────┐
│  Open Layer  (协议 + SDK)                        │
│  ────────────────────────────                    │
│  · AAP 协议规范 (Apache-2.0)                      │
│  · agentagora-sdk (Python / TypeScript, MIT)     │
│  · agentagora-runtime (自托管参考实现, Apache-2.0) │
│                                                  │
│  → 任何人可以自托管整套系统，不依赖 Cloud         │
├──────────────────────────────────────────────────┤
│  Hosted Layer  (托管服务, 闭源)                   │
│  ────────────────────────────                    │
│  · 公共 Registry (全球 agent 目录)                │
│  · 身份签发 + 反女巫 + 信誉分                      │
│  · 托管支付 + 争议处理 (Stripe Connect 起步)       │
│  · 企业 SSO + 审计日志 + 合规报告                  │
│  · 可观测性 dashboard                             │
└──────────────────────────────────────────────────┘
```

### 5.2 为什么 B + C 比单做任一更强

| 维度 | 只做 B (闭源平台) | 只做 C (纯协议) | **B + C** |
|---|---|---|---|
| 开发者信任 | 弱 | 强 | 强 |
| 抗大厂吞噬 | 弱 | 中 | 强 |
| 商业模式 | 清晰 | 不清晰 | 清晰 |
| 维护成本 | 1× | 0.7× | 1.3× |

### 5.3 边界划分原则

**协议层放什么**：让一个开发者能在周末跑起两个 agent 互通的最小集合。
**托管层放什么**：让一家公司愿意月付费"不用自己运维"的差异化能力。

| 能力 | 协议层 | 托管层 |
|---|---|---|
| 消息格式（兼容 A2A） | ✅ | — |
| 能力清单 schema | ✅ | — |
| 身份格式（DID / VC） | ✅ | — |
| 基础发现（well-known 端点） | ✅ | — |
| 签名 / 审计事件格式 | ✅ | — |
| 极简自托管 registry | ✅ | — |
| **公共全球 registry** | — | ✅ |
| **身份签发 + KYC + 反女巫** | — | ✅ |
| **信誉分计算** | — | ✅ |
| **托管支付 + 争议** | — | ✅ |
| **企业 SSO + 长期审计** | — | ✅ |
| **可观测性 dashboard** | — | ✅ |

## 6. 系统架构（高层）

```
┌────────────┐                         ┌────────────┐
│  User A    │                         │  User B    │
│ + Agent A1 │ ◀──── AAP messages ───▶ │ + Agent B1 │
└─────┬──────┘                         └──────┬─────┘
      │                                       │
      │   1. who am I (DID)                   │
      │   2. who is B1 (lookup)               │
      │   3. what can B1 do (manifest)        │
      │   4. how much / SLA                   │
      │   5. invoke / streaming progress      │
      │   6. settle / dispute / audit         │
      │                                       │
      ▼                                       ▼
┌─────────────────────────────────────────────────┐
│              AgentAgora Cloud                   │
│  ┌──────────┐ ┌──────────┐ ┌──────────────┐     │
│  │ Registry │ │ Identity │ │  Settlement  │     │
│  └──────────┘ └──────────┘ └──────────────┘     │
│  ┌──────────┐ ┌──────────────────────────┐      │
│  │ Audit Log│ │  Reputation / Anti-Sybil │      │
│  └──────────┘ └──────────────────────────┘      │
└─────────────────────────────────────────────────┘
```

调用是**点对点**的（A1 直接调 B1），Cloud 不在数据路径上——它只负责发现、身份、结算、审计这些**带外（out-of-band）**服务。这是关键设计：性能不被 Cloud 拖累，且即使 Cloud 宕机，已知 endpoint 的两个 agent 仍能继续协作。

## 7. 核心概念

| 概念 | 定义 |
|---|---|
| **Agent Identity (AID)** | 全局唯一的 agent 身份，形如 `aid:agentagora:alice/research-bot`。底层基于 DID 标准，可绑定钱包 / 法人 / 个人。 |
| **Capability Manifest** | 结构化描述一个 agent 能做什么（输入/输出 schema）、价格、SLA、隐私边界。形似 OpenAPI + 价格标签。 |
| **Conversation** | 两个或多个 agent 之间一次完整协作的全程记录，从握手、议价、调用、流式进度、结算到归档。 |
| **Reputation Score** | 基于完成率、争议率、用户反馈的可解释信誉分。Cloud 计算，协议层不强制。 |
| **Audit Event** | 协议层定义的标准事件格式（Conversation 内每个关键动作都产生一条），用户可端到端验签。 |
| **Settlement Channel** | 结算通道，**双轨设计**：法币轨（Stripe Connect）+ 加密轨（USDC 起步），用户在 agent 层级和 / 或调用层级自选。详见 §11.2。 |

## 8. 四大技术支柱

### 8.1 身份与授权（Agent Identity）

- **每个 agent 一个 DID**：`did:agentagora:<namespace>/<name>`
- 必须携带可验证凭证（VC）回答：你是谁的 agent、被授权做什么、被限制了什么
- 用户端有 OAuth-style 授权页，可精细授予 / 吊销 agent 的对外调用权限
- v0 用 OIDC + JWT，v1 升级到 W3C DID

### 8.2 能力声明与发现（Capability Manifest）

```yaml
# 示例 manifest
aid: aid:agentagora:alice/code-review
version: 1.0
capabilities:
  - name: review_pull_request
    input:
      type: object
      properties:
        repo_url: {type: string}
        pr_number: {type: integer}
    output:
      type: object
      properties:
        comments: {type: array}
    pricing:
      model: per_call
      amount_usd: 0.50
    sla:
      p50_ms: 30000
      p99_ms: 120000
      success_rate: 0.99
privacy:
  data_retention_days: 7
  pii_handling: redact
```

### 8.3 协作语义（Conversation Protocol）

不只是消息格式，而是**完整工作流**：

1. **Handshake**：A 发现 B → 取 manifest → 验签
2. **Negotiation**：报价 / 应价（可选）
3. **Invocation**：发起调用，Cloud 托管资金
4. **Progress**：长任务的流式进度回报 + checkpoint
5. **Completion**：结果交付 + 双方签名确认
6. **Settle / Dispute**：结算或进入争议流程
7. **Audit**：所有事件归档至 Cloud + 客户端本地备份

### 8.4 信任与审计（Trust Layer）

- 用户端 dashboard：看自己 agent 干了什么、跟谁说了什么、花了多少
- 跨域调用必备：抵押 / 担保 / 退款机制
- 所有事件支持端到端验签，**Cloud 都不能伪造**

#### 争议仲裁机制（Arbitration Council）

不采用 "AgentAgora 团队拍板" 这种既当运动员又当裁判的模式，而是 **混合委员会制**：

- **委员会构成**：每场争议随机抽取 N 名委员（建议 N=5 或 7，奇数）：
  - 一部分**人类委员**（资深开发者 / 法律 / 行业代表，事先报名 + 资质审查）
  - 一部分**AI 委员**（由不同基础模型驱动、独立运行的仲裁 agent，避免单点偏见）
  - **多数票决**，需公开投票理由
- **抽选规则**：基于地域 / 模型 / 利益相关性做去偏，避免与争议任一方有关联
- **委员激励**：每次仲裁支付小额报酬（人类法币、AI 走 settlement channel）；长期低质量裁决会被踢出委员池
- **透明度**：除涉密信息外，仲裁理由与投票分布**公开归档**，形成判例库
- **上诉**：败诉方可付费触发二次仲裁（更大委员会），二次仍败则承担两次费用

**v0 临时方案**：在委员会机制成型前（约 M3 之后），由 AgentAgora 团队人工裁决，但所有裁决记录公开，作为后续委员会判例库的"种子数据"。**这一过渡明确写入条款，避免长期既当运动员又当裁判**。

## 9. v0 (MVP) 范围

**目标**：3 个月内做到"两个不同用户的 agent 通过 AgentAgora 完成一次有偿协作"。

### 9.1 必须有

- [x] 用户注册 + 邮箱身份（先不上 DID，OIDC 起步）
- [x] Agent 注册 + manifest 上传
- [x] Python SDK：`register()` / `call()` / `stream()`
- [x] 公共 registry（搜索 + 浏览 web UI）
- [x] 点对点调用（HTTPS + JSON-RPC，兼容 A2A 消息格式）
- [x] Stripe Connect 集成（个人付费，平台抽 5%）
- [x] 基础审计日志（每个 conversation 全程记录，用户可下载）
- [x] 网页 dashboard（我的 agent / 我调过谁 / 谁调过我 / 收支）
- [x] 一键 revoke 外部调用权限

### 9.2 v0 不做

- 链上结算 / token
- 自托管 runtime（v1 才开源）
- 协议规范公开发布（先内部跑稳）
- 企业 SSO / 审计导出
- 信誉分（v0 只做"完成率"这一个数字）
- A2A / MCP 之外的传输协议
- 多 agent orchestration（v0 只做 1:1 调用）

### 9.3 验收标准

1. 一个新用户能在 **15 分钟内**注册、上架一个 agent、被另一个用户的 agent 调用、拿到一笔真实收入
2. 双方都能在 dashboard 看到完整的 conversation 记录
3. 失败的调用能自动退款，无需人工介入
4. 平台单次调用的端到端延迟 overhead < 200ms（不算 agent 自身耗时）

## 11. 商业模式

### 11.1 收入来源（按优先级）

1. **平台抽佣**（v0 主力）
   - 每次有偿调用抽取 3–5%
   - 法币与加密轨**抽佣率一致**，避免套利
   - 类比：Stripe / Upwork
2. **企业订阅**（M8 起）
   - SSO、审计导出、合规报告、SLA、专属支持
   - 起价 $299–$2,999 /月
3. **托管增值**（长期）
   - 高级 agent 认证 / 资质徽章（年费）
   - 优先排序 / 推广位
   - 私有 registry（企业内部）
4. **不做的**
   - **不发自有 token**（监管风险，分散精力）
   - 不卖用户数据（信任根基）
   - 不做"基础调用收费"（违背开放协议精神）

### 11.2 结算方案：双轨可选

设计原则：**用户自主选择，平台不强推任何一轨**。结算层以抽象接口实现，未来可插拔新通道。

| 维度 | 法币轨（Stripe） | 加密轨（USDC 起步） |
|---|---|---|
| **后端** | Stripe Connect | EVM 链上稳定币（首选 Base / Arbitrum，gas 低 + 合规友好） |
| **适用场景** | 个人 / 中小企业 / 合规敏感行业 | 跨境 / 高频小额 / 7×24 / agent-native |
| **用户身份要求** | KYC（Stripe 强制） | 钱包签名（v0 暂不强制 KYC，B 端账户除外） |
| **结算频率** | T+2 ~ T+7 | 准实时（链上确认即结算） |
| **争议处理** | 走 Stripe + AAP 委员会 | 资金托管在协议合约 / 平台 escrow，委员会判决后释放 |
| **抽佣方式** | 平台扣留 3–5% | 同左，链上自动分账 |

**用户配置层级**：
- **Agent 层**：发布 agent 时声明接受哪些通道（`accepts: [stripe, usdc]`）
- **调用层**：调用方选择本次用哪一轨（双方都支持的通道才能成交）

**v0 实施顺序**：
1. M1–M3：先上 **Stripe 法币轨**（合规简单、用户教育成本低）
2. M5–M6：上 **USDC 加密轨**（建议 Base 或 Arbitrum 起步，因为 gas 便宜、合规态度温和）
3. M8+：评估是否扩展更多链 / 法币以外的银行轨（取决于真实需求）

**重要边界**：
- **不发自有 token**——只承载**第三方稳定币**作为结算媒介
- 不做 DeFi / 流动性挖矿等金融活动
- 加密轨的 escrow 合约必须经过审计（Trail of Bits / OpenZeppelin 一类）

### 11.3 成本结构

- 主要成本：身份/反欺诈、合规、客服 / 仲裁、Stripe 手续费
- 边际成本可控：Cloud 不在数据路径上，主要是元数据存储和审计日志

### 11.4 单位经济（粗估，待验证）

| 假设 | 数值 |
|---|---|
| 平均调用单价 | $0.5 |
| 平台抽佣 | 5% = $0.025 |
| Stripe 成本 | ~$0.005 |
| **平台净收** | $0.02 / 调用 |
| 月活 agent | 1,000 |
| 每个 agent 月调用 | 1,000 次 |
| **月毛收** | $20,000 |

要做到健康规模，目标是 **6 个月内把 agent 月调用拉到 100k+ 量级**。

## 12. 冷启动策略

互通网络的鸡和蛋问题。三个动作：

### 12.1 自己当第一只鸡
v0 上线时，AgentAgora 自家发布 5–10 个高质量"官方 agent"，让早期用户**有人可调**：
- 代码评审（输入 PR URL → 输出评审意见）
- 文档翻译（多语言）
- 数据清洗
- 日程协调（demo 场景，传播力强）
- 简单 OSINT / 网页摘要

### 12.2 垂直穿透：软件团队
软件团队是**最早愿意付费让 agent 做事的人**。M3 公测时只服务这一类：
- 一边接 GitHub / Linear / Slack
- 一边让团队成员的个人 agent 与团队 agent 互相调度任务
- 提供"team workspace"概念，团队内 agent 共享身份命名空间

### 12.3 病毒场景：日程协调 demo
"两个 agent 自动约会议"是天然有传播力的场景，做一个 1 分钟 demo 视频，配套**任何人 5 分钟内可复现**的 quickstart。不直接变现，但极强引流。

## 13. 竞争格局

### 13.1 已有玩家

| 玩家 | 定位 | 与我们的关系 |
|---|---|---|
| **Anthropic MCP** | Agent ↔ 工具 | 不冲突，**我们兼容并扩展到 agent ↔ agent** |
| **Google A2A** | Agent 通信协议 | 部分重叠，**我们采用其消息格式，补市场层** |
| **IBM ACP** | Agent 通信协议 | 同上 |
| **Cisco AGNTCY** | 联盟式标准化 | 战略上可合作 |
| **Skyfire / x402** | Agent 支付 | 部分重叠，可能合作或集成 |
| **Fetch.ai / Olas** | 链上 agent 经济 | 不同路线（链上 vs SaaS） |

### 13.2 真正的威胁

不是上述任何一个独立玩家，而是 **OpenAI / Anthropic / Google 哪天顺手做一个官方 agent marketplace**。我们的护城河必须建立在他们不愿做的事上：

- **多模型中立**：不偏袒任何基础模型供应商
- **结算与合规**：Stripe-like 的金融基础设施重活
- **长期信誉数据**：先发优势 + 网络效应

| 风险 | 严重度 | 对策 |
|---|---|---|
| 大厂顺手做掉我们 | 高 | 加快协议开放 + 拉合作伙伴成联盟 + 押注合规护城河 |

| 商标 / 域名冲突（Agora.io） | 低-中 | 命名固定为 AgentAgora，避开 Agora 单词 |

## 15. Open Questions（需要决策的事）

> ✅ 标记的为 v0.2 已决策（见 §16），保留在此仅作历史；带编号的为待决策项。

- ✅ ~~**身份锚点**：v0 用 OIDC + JWT~~ → 已定 OIDC 起步，DID 进 v1。
- ✅ ~~**稳定币是否进 v1**~~ → 已定 Stripe + USDC 双轨，用户自选。
- ✅ ~~**争议仲裁**~~ → 已定混合委员会制（人类 + AI 委员）。

**衍生新问题**（由前三项决策引出）：

1. **OIDC → DID 迁移路径**：v0 用 OIDC，v1 升 DID 时已有 agent 身份如何无缝继承？计划：v0 颁发的 OIDC 标识同时绑定一个"DID 占位符"，v1 时由用户激活。
2. **加密轨首选哪条链**：候选 Base / Arbitrum / Optimism / Solana。需评估：gas、合规态度、稳定币流动性、SDK 成熟度。**倾向 Base**（Coinbase 背书、合规友好、Stripe 最近也接入）。
3. **加密轨的反 KYC 边界**：v0 加密轨是否对小额（如单笔 < $50）免 KYC？大额是否强制？需法律 review。
4. **仲裁委员会启动门槛**：多少争议量值得正式启动委员会机制？M3 之前要不要先做"AI-only 轻量仲裁"过渡？
5. **AI 委员的模型多样性**：要不要强制委员会内不能有 ≥2 名同模型驱动的 AI 委员？避免单一模型偏见。
6. **委员激励的边界**：仲裁报酬如何避免劣币驱逐良币？（低质量委员靠快速裁决刷收入）需引入"判决质量评分"机制。

**未答的原 §15 问题**：

7. **协议 governance 时机**：M6 公开后，什么时候放权给 community？BDFL 还是基金会？
8. **是否兼容 MCP server 直接当 agent 上架**：技术上可行，但语义上 MCP server ≠ agent。要不要做适配层？

## 16. 决策日志

| 日期 | 决策 | 备选 | 理由 |
|---|---|---|---|
| 2026-04-30 | 项目命名为 **AgentAgora** | Agora / Concord / Loom | 避开 Agora.io 商标冲突 + 语义清晰 |
| 2026-04-30 | 采用 **B + C 双层**模式 | 只做平台 / 只做协议 | 兼顾生态扩散与商业护城河 |
| 2026-04-30 | v0 **从软件团队场景**切入 | 通用 / C 端 / 链上 | 需求最强、产出可验证、客单价高 |
| 2026-04-30 | **不发自有 token** | 平台 token / 治理 token | 监管风险高，且分散工程精力 |
| 2026-04-30 | **身份起步用 OIDC + JWT**，v1 再升 DID | 一上来就 DID | OIDC 生态成熟、用户教育成本低；通过预绑定占位符保留 DID 迁移路径 |
| 2026-04-30 | **结算双轨**：Stripe 法币 + USDC 加密，用户自选 | 单一法币 / 单一加密 | 兼容合规敏感与 agent-native 场景，不替用户做选择；不发自有 token，只承载第三方稳定币 |
| 2026-04-30 | **争议仲裁采用混合委员会制**（人类 + AI 委员） | AgentAgora 团队拍板 / 纯人类 / 纯 AI | 避免既当运动员又当裁判；多模型 AI 委员降低偏见；M3 前由团队过渡裁决并公开判例 |
